## Key Question 2: Which Android projects run Windows games, who maintains them, how they work, licensing, and 2026 status

### Takeaway
The ecosystem in Oct 2026 is: **Winlator** (brunodev85/"BrunoSX", MIT, v11.2 Aug 2026, source lags releases) and a large fork tree (Bionic by Pipetto-crypto → Ludashi by StevenMXZ; Cmod by coffincolors/Stredohori (archived May 2026); winebox64 "WB64"; Ajay; Mali builds; Winlator101 by K11MCH1); **GameHub** (GameSir, closed-source, ex-"GameFusion", on Play Store since Nov 2025, v6.x in 2026, plus the de-trackered **GameHub Lite** community rebuild); **GameNative** (Utkarsh Dalal, GPL-3.0, built on Pluvia, FEX + Proton, 1.0 in June 2026, v1.3.0 Oct 2026, ~1M users); **Horizon Emu** (Termux/glibc-based, RuStore/GitHub); and **Mobox** (olegos2, Termux+Box64+Wine, archived Jun 20 2025). FEX-Emu upstream explicitly does not support Android; the Android FEX use is via GameNative's/Winlator-Bionic's forks ("FEXCore").

## Key Question 3: How is the stack layered? (Wine/Proton, Box64/FEX, DXVK/VKD3D, Turnip/Vortek/Gladio, Bionic vs glibc vs PRoot, 16 KB pages, exec restrictions)

### Takeaway
Layering (bottom-up): Android app process → either a **PRoot + Ubuntu glibc rootfs** (classic Winlator), a **native patched glibc** (Winlator 10+/"Glibc" forks), or **Wine built directly against Android Bionic libc** ("Bionic" forks, GameNative) → **Box64** (x86_64 → ARM64 dynarec; or **FEXCore/WowBox64 in ARM64EC Wine**) → **Wine 9.x/10.x or Proton 10/11 (GameNative)** → **DXVK (DX9–11) / VKD3D-Proton (DX12) / D8VK / WineD3D** → Vulkan via **Mesa Turnip** (Adreno), **Vortek** (Winlator's Vulkan proxy to the Android system driver, for non-Turnip GPUs), **Gladio** (GLES wrapper for Mali), **Zink/VirGL** fallbacks. Android's W^X (`execve` denied on app-data files for targetSdk ≥ 29) is why these apps target SDK 28 — an open Oct 2026 PR tries to move Bionic Winlator to targetSdk 34 via `/system/bin/linker64` launching. Wine's ARM64EC mode requires 4 KB pages, so 16 KB-page devices are a live risk.

### Cited Findings

**Wine / Proton versions**

**Bionic vs glibc vs PRoot**
- Classic Winlator: Ubuntu (Focal Fossa) rootfs under **PRoot** (userspace chroot, no root needed) — [Pipetto-crypto README/credits](https://github.com/Pipetto-crypto/winlator); [Habr](https://habr.com/en/news/887128)
- Winlator 10.0 (Mar 2025) "includes glibc with patches… glibc provides higher I/O performance [than Bionic], citing GitHub issue #149"; release note "Added native GLIBC for better I/O performance" — [Habr](https://habr.com/en/news/887128); [brunodev85 releases](https://github.com/brunodev85/winlator/releases)
- winebox64 Q&A "Why does glibc run slower than PRoot on some Android devices?": Bionic is lightweight/mobile-optimized; running glibc "often requires additional compatibility layers, like proot + glibc rootfs"; PRoot syscall translation is slow but its overlay FS can optimize game-data access; glibc games may use more RAM → throttling — [winebox64 releases](https://github.com/winebox64/winlator/releases)
- "Bionic" fork family = builds "built around Android's own Bionic C library instead of glibc"; smaller memory footprint; "occasionally breaks individual games"; "needs custom patches anywhere Windows software assumes glibc behavior" (SEO sources, low confidence) — [tech-insider](https://tech-insider.org/winlator-vs-cmod-vs-bionic-2026/)
- GameNative's "headless bionic Steam client" is "a build for Android's Bionic libc" — [XDA, Jun 27 2026](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/)
- Caution: Winlator Ludashi's credits list "Bionic Beaver" (Ubuntu 18.04) — a different "Bionic" from Android's libc — [search note on Ludashi README](https://github.com/StevenMXZ/Winlator-Ludashi)

**Android exec restrictions / targetSdk**
- Android 10+: "untrusted apps that target Android 10 cannot invoke exec() on files within the app's home directory" (W^X) — [Termux (Wikipedia)](https://en.wikipedia.org/wiki/Termux)
- Pipetto-crypto/winlator **PR #123** ("A solution to bump targetsdk to 34 and minsdk to 28", opened Oct 25 2026, open): Android blocks `execve()` on app-data files for targetSdk ≥ 29; Wine fails when calling `mprotect(PROT_EXEC)` to relocate PE images ("noexec filesystem?"); SELinux denies PROT_EXEC on the process stack; approach 1 was a userspace ELF loader (`libwinloader.so` + LD_PRELOAD shim rerouting exec/posix_spawn); approach 2 (maintainer-suggested) launches binaries as `/system/bin/linker64 <binary>` with a `libexecshim.so`; mprotect fallback narrowed to private file mappings; also fixes an fdsan double-close abort (fatal since targetSdk 30) and re-extracts box64 if missing; tested with two Proton builds and GameNative Proton 11 (x86_64 + arm64ec); author reported "everything seemed to be working" Oct 27 2026; maintainer warned skipping wine-preloader may reduce compatibility — [PR #123](https://github.com/Pipetto-crypto/winlator/pull/123)
- GameNative's Play Store APK "targets newer Android API levels" and drops all-files access/D-drive; the legacy APK keeps them — [XDA](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/)

**16 KB page size**
- Android 15 is the first AOSP release supporting 16 KB-page devices; Pixel 8/8a/9 can boot in 16 KB mode via developer options (Android 15 QPR1+) — [Android Developers](https://developer.android.com/guide/practices/page-sizes); [Android Developers blog](https://android-developers.googleblog.com/2024/08/adding-16-kb-page-size-to-android.html)
- Wine 10.0 notes: ARM64EC requires 4 KB system pages — [UbuntuHandbook](https://ubuntuhandbook.org/index.php/2025/01/wine-10-0-hidpi-scaling-arm64ec/)
- HN comments asserting "Wine doesn't work on 16 KB page size" are unsubstantiated in-thread — [HN](https://news.ycombinator.com/item?id=41331444)
- **No Winlator/GameNative release note or issue about 16 KB pages was found** (searched; upstream release notes contain no mention).

### Inferences
- Vortek is effectively a user-space "Vulkan RPC" that solves two problems at once: ABI mismatch (glibc guest ↔ Bionic driver) and missing Vulkan features on Mali/other drivers. It is the reason Winlator can run at all on 8 Elite before Turnip gen8 matured and on MediaTek/Exynos — at a performance cost.
- The ARM64EC path (Wine 10+ ARM64EC + FEXCore/WowBox64) is architecturally cleaner (Wine itself native, only game code emulated) and is the direction both Winlator Bionic forks and GameNative/Proton are converging on; Valve's Proton-on-Arm work (Steam Frame) lowers the cost of this path.
- Because ARM64EC needs 4 KB pages, 16 KB-page Android devices (possible on future Pixels/others) are a real risk for the ARM64EC lineage; Box64 x86_64 containers do not have the same documented constraint. No source confirms a current shipping phone breaks Winlator for this reason.

### Gaps
- No primary Winlator documentation of the targetSdk value it ships (PR #123 implies the Bionic fork had been below 29); not confirmed for upstream APK.
- No authoritative benchmark comparing Bionic vs glibc vs PRoot (only the winebox64 Q&A and the Habr/issue #149 I/O claim).
- Proprietary Qualcomm driver vs Turnip quantitative comparison not found.

## Key Question 4: How does Steam itself run (GameNative/Pluvia vs Windows Steam client under Wine vs manual copy), and how is Steam DRM / steam_api.dll handled?

### Takeaway
Three models coexist: (1) **run the full x86 Windows Steam client inside Wine+Box64** (classic Winlator, Winlator 10.1+ official Steam support, GameHub for heavy-DRM titles) — slow, RAM-hungry, fragile; (2) **reimplement the Steam network protocol natively (JavaSteam) and skip the client**: GameNative (via Pluvia) logs in/downloads natively and, since 1.0, runs a **headless Bionic-native Steam client** that keeps Steamworks DRM intact, enabled by Valve's Steamworks SDK 1.63 (Nov 2025) adding `linuxarm64`/`androidarm64` libs for Steam Frame; GameHub uses JavaSteam plus **Goldberg** (replaces `steam_api64.dll`, i.e. DRM is bypassed) for light-DRM titles; (3) **copy game files manually** (GOG/DRM-free or Steam folders) into the container. Valve officially says Steam for Linux "is currently not supported on Arm-based hardware" (Oct 2026), though a beta native Arm64 client exists for Steam Frame.

### Cited Findings
- Pre-2026 architecture: "Every app in this space, until very recently… run[s] the full x86 Windows Steam client inside the same Wine and Box64 translation stack that the game itself runs on"; the client renders via CEF, checks updates, syncs cloud, runs overlay, performs DRM checks; each UI frame goes DX→Vulkan via DXVK and each instruction through the Box64 dynarec; launch took "several minutes" on a flagship and failed more often than it succeeded; GameHub's Windows Steam client payload is 41 MB extracted into the Wine prefix — [XDA, Jun 27 2026](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/)
- Valve: Steamworks SDK 1.63 (Nov 2025) added "libs for linuxarm64 and androidarm64" — native ARM64 Steam API libraries for auth, DRM, matchmaking, cloud saves, multiplayer — built for the Steam Frame (SteamOS on Snapdragon, runs Android apps natively); SDK is public — [XDA](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/)
- **GameNative 1.0**: experimental "headless bionic Steam client" (no UI) handling DRM and matchmaking + **JavaSteam** (pure-Java Steam protocol: login + downloads without Wine); enabled per container; beta; reliable only on Proton 10; Half-Life 2 and Portal 2 worked, Cyberpunk 2077 (Proton 11) crashed; online multiplayer inconsistent; library showed 221 of 241 games "compatible" via known configs on an Oppo Find N5 (8 Elite) — [XDA](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/)
- **GameHub tiered approach**: JavaSteam for login/downloads; **Goldberg** (community Steam emulator replacing `steam_api64.dll`, which XDA says "cracks the DRM") for lighter Steamworks DRM; the full Windows Steam client with CEF for everything else — [XDA](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/)
- GameHub 5.0 "full Steam support, including cloud saves"; 5.2 added family sharing; 6.0.6 Steam overlay and lobby invites — [Retro Handhelds](https://retrohandhelds.gg/gamehub-5-0-launches-with-steam-cloud-saves/); [Notebookcheck](https://www.notebookcheck.net/New-GameHub-update-promises-improved-PC-game-emulation-and-Steam-handling-on-Android.1146025.0.html); [Android Authority](https://androidauthority.com/gamehub-606-update-availabe-3675131)
- GameNative also supports Epic, GOG, Amazon; offline play after one-time login or manual file import; Steam ARM Linux client integration was "in testing… could ship in v1.0" (May 2026) — [GitHub](https://github.com/utkarshdalal/GameNative); [DROIX](https://droix.net/blogs/gamenative-vs-gamehub-vs-winlator/); [Android Authority interview](https://www.androidauthority.com/gamenative-interview-kill-handheld-pcs-3664176/)
- Upstream Winlator: 10.1 "adds Steam client support with a hotfix, allowing you to log in and download games directly inside the container" (secondary site); 10.1/11.1 release notes list "Steam Client startup fixes", 11.1 "Steam Legacy in the Start Menu", 11.2 "option to save memory when running Steam games" — [winlator.dev (secondary)](https://winlator.dev/play-games/); [brunodev85 releases](https://github.com/brunodev85/winlator/releases)
- User reports: Steam client "never gets past checking for updates"; client "gets really close to using up all the 6 GB of RAM" — [Steam Community thread](https://steamcommunity.com/discussions/forum/0/601910081412563110)
- Horizon Emu: "Steam client incompatibility" listed as a main drawback — [XDA](https://www.xda-developers.com/horizon-emu-hands-on/)
- SteamCMD is not a substitute: "games that use Steam's DRM need to be run using the client" — [Steam Community](https://steamcommunity.com/discussions/forum/1/601902244366984610)
- Box64 0.4.0 notes: Windows Steam works under Box64; DRM-protected titles needing Windows syscall emulation have platform caveats; ESync/FSync can break Rockstar/Xbox launchers on ARM64 — [box86.org](https://box86.org/2026/01/new-box64-v0-4-0-released/)
- Valve's position: kisak-valve (Oct 5 2026) closed an issue filed from an **AYN Odin 3 running Fedora 44 + a "beta native Arm64 Steam client"** with "Steam for Linux is currently not supported on Arm-based hardware" — [Xenospectrum](https://xenospectrum.com/en/steam-linux-arm-support-boundary/); [steam-for-linux #13689](https://github.com/ValveSoftware/steam-for-linux/issues/13689)
- Armbian forum: Valve published a native ARM64 client ~April 2026; Steam Frame launched Sept 14 2026 (forum claims, unverified) — [Armbian forum](https://forum.armbian.com/topic/62259-native-arm64-steam-client-installer-built-on-rk3588-board-using-the-arm64-steam-frames-client/); Canonical's Steam snap for ARM64 went stable Jun 2 2026 bundling the x86 client under FEX, "outside Valve's support" — [It's FOSS](https://itsfoss.com/news/arm64-steam-snap-goes-stable.md)
- Steam Frame compatibility doc: Snapdragon 8 Gen 3, Arch-based SteamOS; Windows x86 builds run "through Proton and FEX"; FEX passes Vulkan/OpenGL calls to native host libraries and uses code caching to reduce stutter; Lepton runs Android games in a container — [Steamworks docs](https://partner.steamgames.com/doc/steamframe/compatibility)

### Inferences
- The DRM-handling spectrum is: Goldberg (DRM removed; works offline; breaks Steam online features; legally/ToS-grey) ↔ headless Bionic Steam client (DRM intact, Valve-blessed libraries, but only works where the game's Steamworks integration tolerates a headless client) ↔ full Windows Steam client (maximum compatibility, maximum overhead).
- Valve's "not supported on Arm" statement applies to desktop Linux Arm; it does not block the Android apps, which rely only on the public Steamworks SDK ARM libs and the Steam web/CM protocol.

### Gaps
- GameNative's exact DRM mechanism for Steam stub-wrapped executables (steamstub) before 1.0 is not documented in sources found; whether Pluvia/GameNative uses SteamKit (C#) vs JavaSteam — XDA says JavaSteam; original Pluvia repo not fetched.
- No source describes how GameHub decides "light" vs "heavy" DRM per title.

## Key Question 5: Why Snapdragon 8 Gen 2 / 8 Gen 3 / 8 Elite (Gen 5) beat MediaTek / Exynos / Tensor, and the Thor's SoC

### Takeaway
Adreno GPUs are the only mobile GPUs with a mature open-source Mesa Vulkan driver (**Turnip**) that exposes the features DXVK/VKD3D need; Mali (MediaTek/older Exynos/Tensor), Xclipse (newer Exynos) and PowerVR (Pixel 10) must use Vortek/Gladio/Zink/VirGL wrappers over the stock driver with "large" performance losses. In 2026 the **8 Gen 2 / 8 Gen 3 (Adreno 740/750)** are the sweet spot for stability because Turnip is mature there, while the **8 Elite (Adreno 830)** is faster on paper (~2× emulation performance claims) but was "very inconsistent" until community gen8 Turnip builds matured; the Thor's 8 Gen 2 is therefore the stable-but-slower choice.

### Cited Findings
- Turnip "is part of the Mesa 3D graphics library and specifically targets Adreno GPUs"; Mali "lack[s] third-party Mesa drivers like Turnip, and stock Vulkan implementations are often weaker"; MediaTek Dimensity works via Vortek with reduced performance; Adreno+Turnip vs Mali+Zink difference is "large, not a minor difference" — [pocket-gaming.org guide](https://pocket-gaming.org/2026/06/15/the-definitive-guide-to-android-turnip-drivers-hardware-compatibility-2026/); [shattered.io guide](https://shattered.io/winlator-setup-guide/)
- XDA (May 2026): "emulators like GameHub, Eden, and Winlator are very inconsistent on Snapdragon 8 Elite series chips right now, which is why 8 Gen 3 and even older 8 Gen 2 devices are preferred"; Oppo Find N5 (8 Elite) failed even with a8xx beta Turnip; Galaxy Z Fold 5 (8 Gen 2) worked first try with GameHub Lite; "Mesa Turnip has matured well on this older chip" — [XDA](https://www.xda-developers.com/tried-playing-pc-games-only-thing-worked-was-community-rebuild-controversial-app/)
- Community driver recommendations (Apr 2026): Adreno 8xx → StevenMXZ / whitebelyash builds; Adreno 7xx (8 Gen 2/3) → "Mr Purple T25/T26"; Adreno 6xx (865/870) → "K11MCH1 R5" — [DROIX](https://droix.net/blogs/gamenative-vs-gamehub-vs-winlator/); same lists in [XDA](https://www.xda-developers.com/tried-playing-pc-games-only-thing-worked-was-community-rebuild-controversial-app/)
- GameNative dev: 8 Elite and 8 Elite Gen 5 have Turnip support; Hitman WoA runs well, Cyberpunk "occasionally freezes"; Pixel 10 PowerVR and Exynos Xclipse supported via Mesa wrapper — [Android Authority interview](https://www.androidauthority.com/gamenative-interview-kill-handheld-pcs-3664176/)
- Winlator Vortek target list included Snapdragon 8 Elite (before gen8 Turnip) and mid-range 7-series/6-series — [winebox64 releases](https://github.com/winebox64/winlator/releases); Gladio exists specifically for MediaTek/Exynos Mali — [Android Authority](https://www.androidauthority.com/winlator-v11-stable-release-android-pc-emulator-3657643/); GameHub 6.0.6 fixed Mali frame-interpolation issues — [Android Authority](https://androidauthority.com/gamehub-606-update-availabe-3675131)
- 8 Elite "emulation performance roughly two times its predecessor" (claim in Notebookcheck coverage of a social-media clip) — [Notebookcheck, Nov 18 2024](https://www.notebookcheck.net/Snapdragon-8-Elite-allegedly-runs-Cyberpunk-2077-at-60-FPS-via-emulation.920437.0.html)
- Snapdragon 8 Elite Gen 5 announced with ~20% CPU improvement — [GSMArena](https://m.gsmarena.com/newscomm-69656.php); a guide claims Turnip 26.0 "works even with the 8 Elite Gen 5" (SEO, low confidence) — [gamehelptech](https://gamehelptech.com/gamehub-windows-emulator-setup-and-best-settings/)
- Thor's 8 Gen 2 "has better third-party GPU driver support" than the G3x Gen 2 — [Notebookcheck](https://www.notebookcheck.net/AYN-Thor-New-Ayaneo-Pocket-DS-rival-released-globally-from-249.1096976.0.html); DROIX FAQ calls 8 Gen 2 "the most stable generation" while the body credits G3 Gen 3 and 8 Gen 2 with "perfected" drivers (internal inconsistency) — [DROIX](https://droix.net/blogs/gamenative-vs-gamehub-vs-winlator/)
- Mobox docs favored Adreno 6xx or 725–740 "for best performance and compatibility with Turnip+DXVK" — [olegos2/mobox](https://github.com/olegos2/mobox)
- Steam Frame (Valve) itself is Snapdragon 8 Gen 3 — [Steamworks docs](https://partner.steamgames.com/doc/steamframe/compatibility)

### Inferences
- Driver maturity, not CPU speed, is the first-order determinant: a Thor (8 Gen 2) will run a more predictable set of titles than an 8 Elite phone on a bad driver week, but at lower frame rates on heavy titles.
- Valve choosing the 8 Gen 3 for Steam Frame likely accelerates upstream Turnip/FEX/Proton quality for Adreno 750-class parts, which is the generation just above the Thor.

### Gaps
- No quantified Turnip vs proprietary Adreno-driver comparison; no numeric Mali/Xclipse/PowerVR benchmark; nothing on Tensor specifically beyond the Pixel 10 PowerVR note.

## Key Question 6: Real-world performance and what breaks

## Key Question 7: DXVK Async / GPLAsync, shader cache, and Box64 preset ("dynarec") tuning in practice

### Takeaway
DXVK-GPLAsync (async shader compile + GPL cache) is distributed as community "WCP" component packs (2.7.1-1 common; a 3.1.1 ARM64EC build exists) and toggled with `DXVK_ASYNC=1` / `DXVK_GPLASYNCCACHE`; the DXVK state cache (`DXVK_STATE_CACHE_PATH`) is the thing users clear when performance regresses. Box64 presets are bundles of `BOX64_DYNAREC_*` env vars; the Unity/"Stability" preset documented in the wild sets `DYNAREC_BIGBLOCK=3`, `DYNAREC_STRONGMEM=1`, `BOX64_AVX=2`, `BOX64_UNITYPLAYER=0`, with `CALLRET=0` and `WEAKBARRIER` tweaks for Unity. Box64 0.4.4's DynaCache (persistent translated-code cache) is now on by default.

### Cited Findings
- Winlator README: "change the Box86/Box64 preset in Container Settings"; Ludashi: switch preset to "Performance" for x86_64 speed or "Intermediate" to speed up installers; try different FEXCore versions (2505, 2507) for Arm64EC — [Pipetto-crypto README](https://github.com/Pipetto-crypto/winlator); [Ludashi README](https://github.com/StevenMXZ/Winlator-Ludashi)
- Unity preset contents: `DYNAREC_BIGBLOCK=3`, `DYNAREC_STRONGMEM=1`, `BOX64_AVX=2`, `BOX64_UNITYPLAYER=0` — [Bannerlator issue #103](https://github.com/The412Banner/Bannerlator/issues/103); Unity advice `STRONGMEM=1`, `CALLRET=0`, `WEAKBARRIER=0–1` (WEAKBARRIER can cause regressions/crashes) — [thjjfyu/WinlatorWCp](https://github.com/thjjfyu/WinlatorWCp); crash-on-launch → switch to "Stability (Unity Games)" preset — [DeepWiki troubleshooting](https://deepwiki.com/winebox64/winlator/7-troubleshooting)
- WB64 8.5.5 lists "Dynarec Forward & Fast Rounding" as a change — [winebox64 releases](https://github.com/winebox64/winlator/releases)
- Box64 0.4.4: DynaCache enabled by default + Box64-Configurator app — [Phoronix](https://phoronix.com/news/Box64-0.4.4); Box64 0.4.0 work on reclaiming unused dynarec blocks and loop/XMM preloading — [box86.org](https://box86.org/2026/01/new-box64-v0-4-0-released/)
- DXVK-GPLAsync 2.7.1-1 described as "DXVK plus async shader compilation and a GPL cache, aimed at reducing compile stutter"; DXVK 2.5 "not recommended" — [WinlatorWCp](https://github.com/thjjfyu/WinlatorWCp); 3.1.1 gplasync ARM64EC build (toolchain unverified) — [skynetigor](https://github.com/skynetigor/winlator-skynet-components/releases/tag/dxvk-gplasync-3.1.1); benefit smaller on new DXVK since upstream GPL covers most of it — [WinlatorWCPHub](https://github.com/Arihany/WinlatorWCPHub)
- Env vars: `DXVK_ASYNC=1`; `DXVK_GPLASYNCCACHE`; `DXVK_STATE_CACHE_PATH`; upstream `DXVK_STATE_CACHE=0` disables; guidance: clear DXVK cache if performance drops — [DeepWiki DXVK](https://deepwiki.com/winebox64/winlator/6.1-dxvk); [DeepWiki moze30 DX wrappers](https://deepwiki.com/moze30/winlator-glibc/5.1-directx-wrappers-(dxvk-vkd3d-wined3d-d8vk))
- WB64 10.2 ships "DXVK Async v2.6.1" and "DXVK ULL v2.5.3.94" ("aimed at low latency") — [winebox64 releases](https://github.com/winebox64/winlator/releases)
- FEX (Steam Frame) uses code caching to reduce stutter — [Steamworks docs](https://partner.steamgames.com/doc/steamframe/compatibility)
- GameNative "known configs" automatically pick settings per game/device/GPU using ratings + FPS-range telemetry (default-on since Feb 2026) — [Android Authority interview](https://www.androidauthority.com/gamenative-interview-kill-handheld-pcs-3664176/)
- GameHub frame interpolation (its FSR-3-style frame gen) had Mali problems fixed in 6.0.6 — [Android Authority](https://androidauthority.com/gamehub-606-update-availabe-3675131)

### Inferences
- "Preset" tuning is mostly trading dynarec aggressiveness (BIGBLOCK, CALLRET, weak barriers) against memory-ordering correctness (STRONGMEM) for engines like Unity/Mono that rely on x86 TSO semantics; the ARM64EC/FEX path reduces this knob-twiddling because FEX defaults to stricter TSO emulation.
- Shader-cache stutter on first run is the dominant subjective complaint; GPLAsync and persistent caches (DXVK state cache, Box64 DynaCache, FEX code cache) all target first-run stutter, not steady-state FPS.

### Gaps
- No authoritative mapping of Winlator's preset names (Performance/Intermediate/Stability/Compatibility) to full env-var sets for the current 11.x release.

## Key Question 8: Input / controller mapping and handheld form factor

### Takeaway
Winlator relies on Android's standard gamepad APIs and exposes controllers to Windows games as XInput (with DirectInput also improved in 11.0), stores bindings per profile, supports multiple controllers and rumble since 11.0, and added an "XInput raw input extension" plus an input-lag fix in 11.2. An Odin 2 forum report says Winlator "recognizes the Odin's controllers automatically and reports them as XInput"; because the Thor is Odin-2-class hardware, the same behavior is expected but not directly documented. GameHub 6.0.6 adds gamepad-to-keyboard/mouse mapping; Horizon Emu needs a separate InputBridge app.

### Cited Findings
- Winlator controller docs: "relies entirely on Android's standard gamepad APIs"; bindings stored per profile — [Winlator docs mirror (mintlify)](https://mintlify.wiki/brunodev85/winlator/controls/external-controllers) (fetch 503; from search snippet)
- 11.0 Beta: multiple controllers + vibration, better DirectInput/XInput; 11.2: XInput raw input extension, gamepad input-lag fix — [Android Authority](https://www.androidauthority.com/winlator-v11-stable-release-android-pc-emulator-3657643/); [brunodev85 releases](https://github.com/brunodev85/winlator/releases)
- Odin 2 (Spanish forum): Winlator 6.0 recognizes the Odin's controller automatically as XInput — [elotrolado.net](https://www.elotrolado.net/hilo_ayn-odin-2_2485513_s1350); r/OdinHandheld: "Winlator Frosty worked out of the box", glibc variant had a controller issue — [mirror](https://t.sudovanilla.org/r/OdinHandheld/comments/1gz2i98/winlator_controller_on_odin_2)
- GameHub 6.0.6: gamepad-to-keyboard and gamepad-to-mouse mapping; 5.2 better controller/physical keyboard; 6.2.0 controller customization with cloud sharing — [Android Authority](https://androidauthority.com/gamehub-606-update-availabe-3675131); [Notebookcheck](https://www.notebookcheck.net/New-GameHub-update-promises-improved-PC-game-emulation-and-Steam-handling-on-Android.1146025.0.html)
- GameNative: on-screen keyboard and controller overlay — [Android Authority](https://www.androidauthority.com/gamenative-play-steam-games-android-3568963/)
- Horizon Emu: on-screen controls via separate InputBridge app v0.1.9.9; "built-in controls" still a TODO — [Horizon-Emu](https://github.com/HorizonEmuTeam/Horizon-Emu)
- Thor ergonomics: asymmetrical layout, AYN-style clicky D-pad, textured thumb caps, triggers "feel off", power button on bottom edge; reviewer's ergonomics grade "C" without grip, "B" with a $30 JCSFY grip; top screen 6" at 1080p/120 Hz — [Retro Handhelds](https://retrohandhelds.gg/ayn-thor-review/)

### Inferences
- On the Thor, the built-in pad is an Android HID gamepad like the Odin 2's, so Winlator/GameHub will present it as an Xbox/XInput device without extra wrappers; DirectInput-only legacy titles need per-profile bindings.
- The 3.92" bottom screen is irrelevant to PC games (they render on the 6" top screen per the review), but a 1080p top panel means most titles will need 720p internal resolution for playable frame rates.

### Gaps
- No Winlator/GameHub doc or review explicitly tests the Thor's built-in controller with Windows games; no mention of hall-effect sticks or gyro in sources fetched.
