# x86-64 to ARM64 CPU translation layers for Windows games on ARM hosts (Android/Linux vs Apple Silicon macOS), as of 2026-10-27

Scope note: this covers Box64, FEX-Emu, Rosetta 2, Microsoft Prism/ARM64EC, and Wine's own mechanisms (new WoW64, ARM64EC/ARM64X, Hangover, emulator-DLL interface). Dates are given wherever a source states them; "year inferred" is marked where GitHub release pages omit the year. Items older than 2025 are marked as historical. Several primary pages (CodeWeavers blog, Apple's Rosetta-for-Linux page, winehq.org announce, AppleInsider) were blocked by bot protection; where that happened, secondary coverage is cited and the gap is recorded.

## Key question 1: Box64 — architecture, Wine support, 2026 state, AVX/AVX2, performance, macOS

### Takeaway
Box64 is a Linux-only user-mode x86-64 emulator with an ARM64 dynarec that wraps host-native libraries instead of emulating them; in 2026 it ships a 32-bit WoW64 emulator DLL (`wowbox64.dll`) used by Hangover and Winlator, has AVX/AVX2 "fully implemented in DynaRec" on ARM64, and is only now (Sept–Oct 2026) growing an ARM64EC ("box64ec") path targeted at v0.4.6. There is no macOS/Darwin port of Box64 at all.

### Cited Findings
- How it works: Box64 uses a DynaRec (dynamic recompiler) that the README says is 5–10x faster than its interpreter, and it uses the host's native libraries (libc, libm, SDL, OpenGL, etc.) rather than emulating them; supported hosts are ARM64, RV64 and LoongArch (64-bit little-endian); 32-bit binaries need Box86 or the experimental "Box32" mode; it supports Wine64 and Proton; a Wine WOW64 build can run x86 (32-bit) Windows programs on Box64-only setups, "experimental but working in most cases"; MIT licensed — [Box64 README](https://github.com/ptitSeb/box64)
- DynaCache (on-disk cache of generated native code) lives in `~/.cache/box64`, default limit ~2 GB, compressed, controllable by `BOX64_DYNACACHE` (0/1/2) and `BOX64_DYNACACHE_LIMIT` (default 2048 MiB) — [Box64 README](https://github.com/ptitSeb/box64); [docs/USAGE.md](https://github.com/ptitSeb/box64/blob/main/docs/USAGE.md)
- Release cadence (dates from GitHub API): v0.4.4 published 2026-08-02; v0.4.2 2026-04-20; v0.4.0 2026-01-03 — [Box64 releases](https://github.com/ptitSeb/box64/releases)
- v0.3.4 (10 Mar 2025): added Windows syscall emulation ("needs Proton and a 48-bit address space"), GDBJIT, and CI builds producing MiceWine `.rat` and Winlator `.wcp` archives — [Box64 releases](https://github.com/ptitSeb/box64/releases)
- v0.3.6 (06 Jun 2025): "introduces wowbox64.dll for Hangover", lets x64 Wine use Windows executables' volatile metadata, adds x87 precision-control handling and more precise NaN/rounding in SSE and AVX, adds `.box64rc` in Wine prefixes — [Box64 releases](https://github.com/ptitSeb/box64/releases)
- v0.3.8 (13 Oct 2025): introduced DynaCache (not yet default), "WOW64 minimal Windows runtime and preliminary WowBox64 support", Starfield works — [Box64 releases](https://github.com/ptitSeb/box64/releases)
- v0.4.0 (03 Jan 2026): dynarec prefix-decoder refactor, FSGSBASE, more DRM-protected games run; "DRM protected stuff that need Windows Syscall emulation will not work for now unless the hardware support SV48 (48bits address space) or using a hacked Wine/Proton" — [Box64 releases](https://github.com/ptitSeb/box64/releases); [box64 v0.4.0 via newreleases.io](https://newreleases.io/project/github/ptitSeb/box64/release/v0.3.0)
- v0.4.2 (20 Apr 2026): PPC64LE backend, Vulkan x64 overlay support (Steam client/Fossilize/GameOverlayUI), major ARM64/LoongArch dynarec refactors fixing speed regressions, SteamRT3 and Proton 11 support — [Box64 releases](https://github.com/ptitSeb/box64/releases)
- v0.4.4 (02 Aug 2026): DynaCache enabled by default (compressed, up to 2 GB), `BOX64_AVX=2` setting reworked, AVX enabled by default on LoongArch, better DRM-game accuracy — [Box64 releases](https://github.com/ptitSeb/box64/releases)
- AVX/AVX2 status: `BOX64_AVX` = 0 (none) / 1 (AVX, BMI1, F16C, VAES) / 2 (adds AVX2, BMI2, FMA, ADX, VPCLMULQDQ, RDRAND); default is 2 on Arm64 and LoongArch64 "where it is fully implemented in DynaRec", 0 elsewhere; RV64 has only scalar AVX (v0.3.8 notes) — [docs/USAGE.md](https://github.com/ptitSeb/box64/blob/main/docs/USAGE.md); [Box64 releases](https://github.com/ptitSeb/box64/releases)
- Memory-model/accuracy knobs: `BOX64_DYNAREC_STRONGMEM` 0 (default) to 4 (level 4 "mimics x86 TSO similar to QEMU", evaluation only); `BOX64_DYNAREC_FASTNAN` default 1; `BOX64_DYNAREC_X87DOUBLE` default 0 (float where possible); `BOX64_DYNAREC_BIGBLOCK` 3 "useful for Wine programs" — [docs/USAGE.md](https://github.com/ptitSeb/box64/blob/main/docs/USAGE.md)
- Wine variants per Box64's own guide: x86_64 Wine WOW64 (x32 + x64 EXEs) needs only Box64 "because Wine handles the 32-bit emulation" (WineD3D slow for 32-bit; DXVK recommended); Arm64 Wine WOW64 needs "a cpu.dll ... known as the WOW64 (for 32-bit) and Arm64EC (for 64-bit)"; Box64 supports the 32-bit WOW64 DLL via the `WOW64` CMake option and "we plan to support Arm64EC in the future"; for Arm64 Wine the guide recommends Hangover — [docs/WINE.md](https://github.com/ptitSeb/box64/blob/main/docs/WINE.md)

- Historical (2023): Wine WoW64 on Box64 was described as alpha quality — [box64 discussion #863](https://github.com/ptitSeb/box64/discussions/863)
- 16K pages (historical, 2024): Box64 0.2.8 (reported 22 May 2024) "adds support for running Linux games on systems with a 16K page size", explicitly for M1/Apple Silicon Linux kernels; Unity titles reportedly play fine — [Phoronix, Box64 0.2.8](https://www.phoronix.com/news/Box64-0.2.8-Released)
- Fedora's assessment of that 16K support: "box64 handles 16k kernels only through hacks that support a limited set of x86_64 apps ... not a general solution and breaks with programs such as Wine" — [Fedora Changes/FEX](https://fedoraproject.org/wiki/Changes/FEX)
- Winlator (the Android app) runs Wine + Box86/Box64; official minimums for Winlator WB64 are Android 9.0+, Snapdragon 460-class CPU, Vulkan 1.1 — [winebox64/winlator](https://github.com/winebox64/winlator)
- Winlator-Ludashi (Bionic fork) offers two container types: "x86_64 containers" (Box86/Box64) and "Arm64EC containers" using FEXCore for 64-bit and 32-bit, "or optionally WowBox64 for 32-bit only"; FEXCore versions (e.g. 2505, 2507) are selectable per container — [StevenMXZ/Winlator-Ludashi](https://github.com/StevenMXZ/Winlator-Ludashi); [TripleJ160/winlator-ludashi-plus](https://github.com/TripleJ160/winlator-ludashi-plus)

- Performance (historical, Mar 2022, Raspberry Pi 400): 7-Zip Box64 3084 vs FEX x86_64 1486 vs native aarch64 5787; dav1d 1-thread Box64 49.72 vs FEX 27.28 vs native 185.57; glmark2 Box64 178 vs FEX 164 vs native 181; on an M1 (7z) Rosetta 2 reached ~71% of native and Box64 ~57% — [box86.org benchmark](https://box86.org/2022/03/box86-box64-vs-qemu-vs-fex-vs-rosetta2/)
- Performance (Cortex-A53, foo2zjs driver): native ~7.8 s, Box64 stock ~26.1 s, Box64 tuned ~19.2 s, FEX ~20.3 s — [UoWPrint blog](https://printserver.ink/blog/box64-vs-fex/)
- Fedora's view: "performance is similar between box64 and FEX, and both are steadily improving" — [Fedora Changes/FEX](https://fedoraproject.org/wiki/Changes/FEX)
- macOS: the README, releases page and docs contain no macOS/Darwin mention; GitHub issue search for "macOS"/"Darwin" in ptitSeb/box64 returns only Asahi-Linux-on-Mac issues (e.g. #487 "Wine64 gives an error on fedora 37 running on an M1 mac", 2022; #1778 Asahi Fedora 40, 2024) — [Box64 README](https://github.com/ptitSeb/box64); [box64 issue #487](https://github.com/ptitSeb/box64/issues/487); [box64 issue #1778](https://github.com/ptitSeb/box64/issues/1778)

### Inferences
- "Running Wine with Box64" on Android/Linux today means one of two very different things: (a) Box64 emulating an entire x86-64 Wine process (classic Winlator "x86_64 container"), or (b) native ARM64 Wine loading `wowbox64.dll` purely as the 32-bit CPU emulator (Hangover default, Winlator "Arm64EC container" with WowBox64 for 32-bit). Until the `box64ec.dll` work lands (slated for v0.4.6), Box64 cannot be the 64-bit emulator in mode (b); FEX fills that role.
- The absence of any Darwin code path, combined with Box64's reliance on Linux ELF loading and wrapping of Linux host libraries, makes a native macOS Box64 effectively a from-scratch port; nobody appears to have attempted it publicly.

### Gaps
- No primary source found for Box64's current percent-of-native on modern hardware (Snapdragon X / M-series); the only cross-emulator numbers are from 2022 and a 2025-era A53 test.
- Could not find a Box64 document describing a page-size variable for Android 16K devices; the 0.2.8 note is the only 16K statement located.
- Box64's `[ARM64EC]` PRs are merged but v0.4.6 is not released as of the GitHub API check (latest is v0.4.4, 2026-08-02); whether `box64ec.dll` runs real games is unknown.

## Key question 2: FEX-Emu — architecture, Wine WoW64/ARM64EC backend, Valve/Proton, Fedora/Asahi, AVX, 16K pages, macOS portability

### Takeaway
FEX is a Linux user-mode x86/x86-64 JIT that, when compiled with llvm-mingw as `libarm64ecfex.dll` (x86-64, ARM64EC ABI) and `libwow64fex.dll` (32-bit WoW64), becomes a pure CPU-emulator plugin that native ARM64 Wine loads via the Windows `HKLM\Software\Microsoft\Wow64\amd64` mechanism; it is what Valve ships in Proton 11 for ARM64EC builds and what Fedora/Asahi use. Upstream has repeatedly said it has no macOS plans and requires 4K-page kernels, but by 2026 four independent macOS ports (CodeWeavers' private one, FEX-darwin, MetalSharp's fork, Zagrios/FEX) exist.

### Cited Findings
- FEX's site states it can serve as a WoW64/ARM64EC backend for Wine — [fex-emu.com](https://fex-emu.com/)
- FEX-2501 (Jan 2025) added a Ubuntu PPA package `fex-emu-wine` that "supplies WoW64 and ARM64EC emulator DLLs for an AArch64 Wine build" — [FEX-2501 released (linuxcompatible)](https://www.linuxcompatible.org/story/fex2501-released/)
- Architecture of the Windows modules: "The Windows FEX modules handle only CPU emulation. Syscall translation happens on the Wine side (WOW64) or in the ABI (ARM64EC)"; therefore native ARM64 `.so` libraries (Vulkan, Wine) are used and "no x86 rootfs or FEX-side thunking is needed"; FEX "loads very early and can depend only on ntdll, not the system CRT", so a CRT/WinAPI subset is stubbed under `Common/Windows/{WinAPI,CRT}`; ARM64X combines ARM64EC and ARM64 code in one binary — [FEX wiki: Development:ARM64EC](https://wiki.fex-emu.com/index.php/Development:ARM64EC)
- Build: FEX is built twice with the bylaws llvm-mingw toolchain — ARM64EC module targets `arm64ec-w64-mingw32`, WOW64 module targets `aarch64-w64-mingw32`; Wine configured with `--enable-archs=arm64ec,aarch64,i386 --with-mingw=clang`; the bylaws Wine fork is recommended "because upstream Wine lacks some FEX/ARM64EC support"; DXVK/vkd3d-proton built with an `arm64ec-w64-mingw32` Meson cross file — [FEX wiki: Development:ARM64EC](https://wiki.fex-emu.com/index.php/Development:ARM64EC)
- On real Windows on Arm, ARM64EC FEX "can replace xtajit64": copy `libarm64ecfex.dll` into `C:\Windows\System32` and set `HKLM\Software\Microsoft\Wow64\amd64` to `libarm64ecfex.dll`; replacing the x86 WOW64 path (`...\Wow64\x86`) "doesn't work and causes all 32-bit applications to hang" — [FEX wiki: Development:ARM64EC](https://wiki.fex-emu.com/index.php/Development:ARM64EC)
- Maintainer (Sonicadvance1, 2026-03-13): FEX's Wine integration "uses the same APIs that Microsoft's XTA/Prism uses on Windows, so FEX can act as a drop-in replacement"; user report 2026-04-29: `libarm64ecfex.dll` works for 64-bit apps on Windows, `libwow64fex.dll` hangs; collaborator bylaws: the WOW64 path on Windows is "untested and crashes weirdly" — [FEX discussion #5367](https://github.com/FEX-Emu/FEX/discussions/5367)
- Release train (GitHub release dates; year from API for the latest): FEX-2604 (09 Apr), FEX-2605 (09 May), FEX-2607 (04 Jul), FEX-2608 (05 Aug), FEX-2609 (08 Sep), FEX-2610 (published 2026-10-07) — [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- FEX-2603: vzeroupper/vzeroall zeroing moved to DC ZVA; "Death Stranding going from 55 to 70 FPS on AmpereOne" in their test scene; known steamwebhelper crash — [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- FEX-2604: Arm64EC dispatcher rearranged, suspend doorbell out of hot path; inline x87 SIN/COS/TAN average 3.7x speedup; memory reduced via Dynamic L1 and disabling L2 lookup caches; new config shows TSO fault granularity ("FEAT_LSE2 reduces faults within a 16-byte granule, but many accesses still fault") — [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- FEX-2605: fixed an ARM64EC crash with controllers (suspend-doorbell race); Snapdragon X2 Elite: RNDRRS broken so RNG disabled, 19.2 MHz cycle counter, 128-bit SVE2, SME, KVM; "RMW atomics only SIGBUS at 64-byte boundaries, but acquire/release instructions still SIGBUS at 16-byte boundaries"; split-lock emulation via SIGBUS, still "no way to emulate cacheline-straddling split locks without tearing" — [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- FEX-2607: added a unixlib ("shipping two DLLs and two unixlib SO files", optional); work on 256-bit paths for future SVE2 hardware; "all AVX instructions now zero extend their results as expected"; fixes for Mafia 3 and Bioshock on Arm64EC Proton — [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- FEX-2608: spinloops use WFE on WINE; VirtualProtect fixed on Win32; AVX signal-state save/restore fixed — [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- FEX-2609: removed unixlib fallbacks; "found Windows syscalls could be made when FEX replaced XTAJIT/Prism"; faster SMC detection, less JIT lock contention — [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- FEX-2610: "WOW64 uses CHPEv2 for suspend and exception support"; ARM64EC NT syscall numbers no longer hardcoded; AVX-VNNI added; DiskCache enabled by default for Steam builds; disk cache capped at 1 GB; software RDRAND/RDSEED fallback for Qualcomm Oryon (buggy RNG), off by default — [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- AVX design history: originally AVX emulation "required SVE2 with 256-bit registers", which no Apple Silicon has (M1–M3, A17 lack SVE/SVE2, Jan 2024); on 2024-06-24 Alyssa Rosenzweig said the approach changed — "AVX on top of 128-bit is in progress and should work even on M1 using ASIMD" (accepted answer) — [FEX discussion #3267](https://github.com/FEX-Emu/FEX/discussions/3267)
- Page size: "FEX only supports systems running 4k page-size kernels"; Fedora Asahi Remix uses 16K, so muvm runs FEX in a microVM with a 4K-page kernel; muvm/16K integration was still a TODO as of 2024-10-14 — [Fedora Changes/FEX](https://fedoraproject.org/wiki/Changes/FEX); FEX issue #1221 (2021) "Throw an error when compiling and running on a non-4k page host" — [FEX issue #1221](https://github.com/FEX-Emu/FEX/issues/1221)
- Fedora chose FEX over box64 (Fedora 42 change, owners Davide Cavalca, Neal Gompa, Alyssa Rosenzweig; Asahi SIG/KDE SIG) because FEX supports both x86 and x86_64 and box64 (then) lacked x86, "which matters for software like Steam"; packaging: `fex-emu`, a Kiwi-built RootFS RPM, muvm, hidpipe, sommelier; thunks not yet packaged — [Fedora Changes/FEX](https://fedoraproject.org/wiki/Changes/FEX)
- Asahi "AAA gaming" stack (2024-10-10): Asahi (16K pages) → muvm microVM with 4K-page kernel, GPU/controllers passed through → FEX → Wine → DXVK/vkd3d-proton, Honeykrisp Vulkan 1.3 driver; "most games need 16GB of memory because of emulation overhead"; AAA titles not yet 60 fps, indie titles full speed — [Asahi Linux blog](https://asahilinux.org/2024/10/aaa-gaming-on-asahi-linux/)
- Valve/Proton: Proton 11.0-beta1 (16 Apr): "Added FEX-2604 for ARM64EC builds"; proton-11.0-1-beta3 (13 May): "This is a small update affecting ARM64 only. Updated to FEX-2605"; Proton 11.0-1 (07 Jul): "Added FEX-2605 for ARM64EC builds"; Proton 11.0-2 (21 Aug): "Updated to FEX-2607"; 11.0-2e (09 Oct) — [Proton releases](https://github.com/ValveSoftware/Proton/releases)

- Upstream macOS stance: 2023-11-11 "No plans to support macOS"; issue #5046 "Mac Support" (2025-11-13): Sonicadvance1 "There are no plans for MacOS support in FEX at this time" (closed) — [FEX discussion #3267](https://github.com/FEX-Emu/FEX/discussions/3267); [FEX issue #5046](https://github.com/FEX-Emu/FEX/issues/5046)
- Historical compatibility note (Mar 2022): FEX could not run Wine for CINEBENCH and had no sound in games, while Box ran Wine with sound — [box86.org benchmark](https://box86.org/2022/03/box86-box64-vs-qemu-vs-fex-vs-rosetta2/)

### Inferences
- The Windows-DLL form of FEX is architecturally portable: it depends only on ntdll-level APIs and gets its syscalls from the ARM64EC ABI/Wine, which is exactly why the macOS ports (see Q7) could be done by patching page-size, JIT-protection and shared-data assumptions rather than re-implementing a Linux syscall layer. A native macOS port of the standalone Linux `FEXInterpreter` would be a far larger job (Linux syscall emulation on Darwin) — which is what Zagrios/FEX attempts by having a host program serve Linux syscalls.
- Valve's choice to ship FEX inside Proton ARM64EC builds (not Box64) makes FEX the de-facto reference x86-64 CPU backend for Wine on ARM64 Linux in 2026.

### Gaps
- No FEX release note explicitly discusses 16K/non-4K page support; the 4K-only requirement is documented by Fedora and the 2021 issue, not by a current FEX doc fetched here.
- "Lepton" (mentioned by GamingOnLinux alongside Proton on Steam Frame) is not defined in any fetched source; Steam Frame hardware specs were not found.
- FEX-2606 does not appear in the releases list; unknown whether it was skipped.
- No stable (non-beta) statement from Valve about Proton ARM64 on non-Frame hardware was found beyond the changelog lines.

## Key question 3: Rosetta 2 — what it translates, AVX2, limits, JIT/AOT, CrossOver/GPTK usage, performance, deprecation timeline

### Takeaway
Rosetta 2 is a whole-process x86-64 Mach-O (and, via Virtualization.framework, x86-64 Linux ELF) translator; Apple's current doc says it translates "all x86_64 instructions, including AVX and AVX2" (AVX2 arrived with macOS 15) but never AVX-512; Apple's June 2025 statement keeps it "through macOS 27" as a general tool and thereafter only "a subset of Rosetta functionality aimed at supporting older unmaintained gaming titles". CrossOver 26 still runs Wine entirely under Rosetta; CodeWeavers' answer is a native ARM64 Wine + private macOS FEX port in CrossOver Preview (July 2026) / CrossOver 27 (early 2027).

### Cited Findings
- Apple's doc: Rosetta translates "most Intel-based (x86_64) Mac apps, including apps with just-in-time (JIT) compilers" and "all x86_64 instructions, including AVX and AVX2"; it does not translate kernel extensions, "virtual machine apps that virtualize x86_64 computer platforms", or AVX-512 (check `hw.optional.avx512f`); "Rosetta applies to the entire process, including dynamically loaded code modules. The system doesn't allow mixing arm64 and x86_64 code in the same process"; detection via `sysctl.proc_translated` — [Apple: About the Rosetta translation environment](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment)
- Deprecation statement (same page): "Rosetta was designed to make the transition to Apple silicon easier, and will be available through macOS 27 — as a general-purpose tool for Intel apps to help developers complete the migration of their apps. Beyond this timeframe, we will keep a subset of Rosetta functionality aimed at supporting older unmaintained gaming titles, that rely on Intel-based frameworks." — [Apple: About the Rosetta translation environment](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment)
- The doc was updated after the WWDC keynote of 9 June 2025; MacRumors reported it 10 June 2025 — [MacRumors](https://www.macrumors.com/2025/06/10/apple-to-phase-out-rosetta-2/)
- Rollout mechanics (Aug 2026 reporting): since macOS 26.4 (March 2026) launching an Intel-only app shows a banner that it won't open in a future release; in macOS 27 ("Golden Gate") upgrading removes Rosetta and prompts for reinstall on first need, with a Settings > General > About > Details list of apps needing Rosetta; in macOS 28 (author calls it "Dumbarton", fall 2027) Intel-only apps and components stop working; Apple's support wording for the exception is "certain older, unmaintained games that rely on Intel-based frameworks" — [Six Colors](https://sixcolors.com/post/2026/08/preparing-for-next-years-rosetta-2-demise/); [highball issue #6](https://github.com/gauthierpiarrette/highball/issues/6)
- Unity's guidance describes a macOS 27 beta-only tool for checking whether a game still runs on Apple's legacy layer, to be removed before 27 GA — [Unity Discussions](https://discussions.unity.com/t/apple-rosetta-deprecation-and-your-mac-intel-based-games-what-to-do-and-when/1724774)
- AVX history (historical): Apple's earlier doc wording was that Rosetta "doesn't support AVX, AVX2, and AVX512" — [HN 2020 thread quoting the doc](https://news.ycombinator.com/item?id=25547896)
- AVX2 arrival: a June 2024 experiment on the macOS 15.0 beta tested AVX/AVX2 under Rosetta — [rosetta2_avx_dive](https://github.com/carsongoodwin32/rosetta2_avx_dive); FEX discussion noted on 2024-06-11 that "Apple added AVX(2) support in macOS Sequoia beta" — [FEX discussion #3267](https://github.com/FEX-Emu/FEX/discussions/3267)
- CPUID under-reporting: Go commit 9125351583 (2025-08-29, "internal/cpu: report AVX1 and 2 as supported on macOS 15 Rosetta 2"): "on macOS 15 or newer, Rosetta 2 supports AVX1 and 2. However, neither CPUID nor the Apple-recommended sysctl says it has AVX. ## Key question 4: Wine's own ARM64 story — new WoW64, ARM64EC/ARM64X, emulator-DLL interface, Hangover, running x86-64 apps without wrapping Wine

### Takeaway
Since Wine 10.0 (Jan 2025) Wine on ARM64 is built as PE/ARM64EC with a 64-bit x86 "emulation interface" where Wine's own code runs natively and only the application's x86-64 code is emulated by an external DLL named in `HKLM\Software\Microsoft\Wow64\amd64`; Wine 11.0 (13 Jan 2026) made the new WoW64 mode fully supported and added a (weak) 4K-page simulation on 16K/64K kernels. Hangover is now "around ten patches atop upstream Wine" bundling FEX (64-bit default) and Box64's WowBox64 (32-bit default), so running x86-64 Windows apps in native ARM64 Wine without Box64 wrapping the process is the mainstream path on Linux in 2026.

## Key question 5: Microsoft Prism (Windows on ARM) as comparison

### Takeaway
Prism (Windows 11 24H2+) is Microsoft's JIT x86/x64→ARM64 emulator with a per-module translation cache service; x86 runs through a WOW64 layer while x64 runs with no WOW64 layer because system DLLs are Arm64X hybrids; AVX/AVX2/BMI/FMA/F16C emulation shipped to general availability with the Oct 2025 KB5066835 update (on by default for x64 apps only). FEX uses the same emulator-plugin interface and can replace Prism's `xtajit64.dll` on real Windows for 64-bit apps.

### Cited Findings
- Prism is the new emulator in Windows 11 24H2 with "significant optimizations that improve the performance and lower CPU usage"; "optimized and tuned specifically for Qualcomm Snapdragon processors. Some performance features within Prism require hardware features only available in the Snapdragon X series"; "just-in-time compiling blocks of x86 instructions into Arm64 instructions"; "A service caches these translated blocks of code ... caches are produced for each module so that other apps can make use of them on first launch"; x86 apps go through WOW64 with filesystem/registry redirection; "For x64 apps, there's no WOW64 layer ... system binaries are compiled as Arm64X PE files"; user-mode only, drivers must be Arm64; apps see an emulated virtual processor in CPUID/`GetNativeSystemInfo`; page dated 2025-11-06 — [Microsoft Learn: How emulation works on Arm](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation)

### Inferences
- Prism's x64 model (no WOW64 layer, Arm64X system DLLs, emulator DLL plugged in via the `Wow64\amd64` key) is exactly the model Wine 10+/Hangover copy on Linux and the macOS forks copy on Darwin; the Windows ecosystem and Wine now share an emulator plugin ABI (CHPEv2/ARM64EC), which is why FEX is interchangeable between the two.

## Key question 6: Comparing the approaches (whole-process Box64 vs native Wine + per-process x86 emulation vs whole-process Rosetta) — performance, compatibility, memory, page size, JIT permissions, SSE/AVX

### Takeaway
All three current stacks converge on the same idea for the 64-bit case — keep the host-side Wine/Proton native and emulate only the Windows x86-64 code through an ARM64EC emulator DLL — with the exceptions being legacy Winlator "x86_64 containers" (Box64 emulates all of Wine) and CrossOver ≤26 (Rosetta translates all of Wine). The decisive platform differences are page size (Linux: 4K kernel or microVM; Android: device-dependent; macOS: 16K unless the 26.5 4K-spawn attribute + restricted entitlement is used), JIT policy (macOS MAP_JIT/W^X and entitlements vs Linux mprotect), and memory ordering (macOS exposes hardware TSO via `thread_set_x86_64_compat`, Linux emulators pay barrier costs or fault-based TSO).

### Cited Findings
- Whole-process emulation vs plugin: Hangover "emulate[s] only the target application, not a full Wine installation" and Win32/Unix calls run natively — [Hangover README](https://github.com/AndreRH/hangover); Wine 10.0: "Wine's own code runs natively, and only the application's x86-64 code is emulated" — [Wine 10.0 ANNOUNCE (mirror)](https://raw.githubusercontent.com/wine-mirror/wine/wine-10.0/ANNOUNCE.md); Rosetta: whole process, no mixing of arm64/x86_64 — [Apple Rosetta doc](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment)
- FEX Windows modules need no x86 rootfs or thunks because syscalls are translated on the Wine side, and native ARM64 Vulkan/Wine `.so` files are used — [FEX wiki](https://wiki.fex-emu.com/index.php/Development:ARM64EC); by contrast Linux FEX needs a RootFS (Fedora packages a Kiwi-built RootFS; podman-fex uses a ~1.8 GB EROFS RootFS) — [Fedora Changes/FEX](https://fedoraproject.org/wiki/Changes/FEX); [podman-fex](https://github.com/tnk4on/podman-fex); Box64 instead wraps host-native libs — [Box64 README](https://github.com/ptitSeb/box64)

- x87 precision: Box64 defaults to float where possible (`X87DOUBLE=0`) — [Box64 USAGE.md](https://github.com/ptitSeb/box64/blob/main/docs/USAGE.md); MetalSharp "x87 uses double precision by default for speed, at a cost in precision" and Ori's audio needs x87 handling — [MetalSharp-Wine](https://github.com/metalsharp/MetalSharp-Wine)
- Memory: Asahi's stack "most games need 16GB of memory because of emulation overhead" — [Asahi blog](https://asahilinux.org/2024/10/aaa-gaming-on-asahi-linux/); FEX-2604 reduced memory by enabling Dynamic L1 and disabling L2 lookup caches by default — [FEX releases](https://github.com/FEX-Emu/FEX/releases); Box64 DynaCache uses up to 2 GB disk; FEX disk cache capped at 1 GB — [Box64 README](https://github.com/ptitSeb/box64); [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- Performance anchors: Rosetta ~71% vs Box64 ~57% of native on 7-Zip (M1, 2022) — [box86.org](https://box86.org/2022/03/box86-box64-vs-qemu-vs-fex-vs-rosetta2/); Fedora: FEX ≈ Box64 — [Fedora Changes/FEX](https://fedoraproject.org/wiki/Changes/FEX); Death Stranding 55→70 fps on AmpereOne from one FEX change — [FEX releases](https://github.com/FEX-Emu/FEX/releases); MetalSharp claims JIT-time rebasing cut constant-address loads from "1.7 µs" to 0.3 ns per read and cold dnsapi startup from 10.5 s to ~0.6 s (self-reported, no methodology) — [MetalSharp-Wine](https://github.com/metalsharp/MetalSharp-Wine); Proton ARM64 beta described as "inconsistent in performance" — [XDA](https://www.xda-developers.com/valve-isnt-ditching-windows-x86-quietly-making-optional/)
- Compatibility, 32-bit: Hangover/FEX WOW64 path is the less mature one (hangs on Windows; Box64's `wowbox64.dll` is Hangover's default for i386) — [FEX discussion #5367](https://github.com/FEX-Emu/FEX/discussions/5367); [Hangover README](https://github.com/AndreRH/hangover); CrossOver 27 drops 32-bit bottles entirely — [CodeWeavers CrossOver 27 post (JS-gated)](https://www.codeweavers.com/blog/mjohnson/2026/6/11/whats-in-and-whats-out-for-crossover-27); MetalSharp's i386 needs macOS 26.4+ and a signed app — [MetalSharp-Wine](https://github.com/metalsharp/MetalSharp-Wine)
- DRM: Box64 needs SV48 48-bit address space for Windows syscall emulation used by DRM — [Box64 releases](https://github.com/ptitSeb/box64/releases); FEX has a long-open "Denuvo needs inline self-modifying code support" issue (#2841, 2023) — [FEX issue #2841](https://github.com/FEX-Emu/FEX/issues/2841)

### Inferences
- Model A (Box64 wraps all of Wine, classic Winlator) pays translation cost on Wine's own code and every Win32→Unix transition, and inherits Box64's library-wrapping limits; Model B (native Wine + FEX/WowBox64 DLL) confines translation to the game's code and lets Wine, DXVK, Vulkan drivers run native, matching Prism's design; Model C (Rosetta whole-process) pays for translating Wine too but benefits from Apple's AOT translation, hardware TSO mode, and a 4K-page process environment for free — which is why Rosetta Wine "just worked" with 4K Windows assumptions while native ARM64 Wine on macOS needed macOS 26.5 APIs.
- On Android, the Winlator "Arm64EC container" is model B and the "x86_64 container" is model A; page size on Android depends on the device kernel (not sourced here) and would affect both models the same way Wine's 4K simulation does on Linux.
- macOS's hardware TSO (via `thread_set_x86_64_compat`) is a potential performance advantage for FEX-on-macOS over FEX-on-Linux-ARM, since Linux FEX currently pays fault/barrier costs for TSO; MetalSharp chose not to use hardware TSO, so this is unexploited in the public forks as of Oct 2026.

### Gaps
- No apples-to-apples 2025–2026 benchmark across Box64, FEX, Rosetta and Prism on the same hardware was found.
- Android 16K-page device behaviour with Box64/Winlator is unsourced; the Box64 16K statement concerns Linux on Apple Silicon.
- Memory footprints for the Wine+FEX plugin model vs Rosetta Wine were not quantified by any source.

## Key question 7: Attempts to run Box64 or FEX natively on macOS, and FEX inside Linux VMs on macOS

### Takeaway
Box64 has no macOS attempt at all. FEX has four independent 2025–2026 macOS lines: CodeWeavers' private port (Nov 2025 FEX integration, macOS-compatible FEX finished July 2026, shipped in CrossOver Preview 31 Jul 2026, sources due with CrossOver 27 in early 2027), the FEX-darwin Wine-module port (FEX-2609.1 base), MetalSharp-Wine's FEX fork (Wine 11.20, macOS 15+/26.4+), Irz-Z/wine-macos-native v0.1.0 (Wine 11.10 + in-process FEX), and Zagrios/FEX (FEXCore-only Darwin port for a Linux-syscall host). FEX-in-a-VM on Mac exists as Asahi muvm (Linux host) and podman-fex (libkrun on macOS, Apr 2026 preview).

### Cited Findings
- FEX upstream: "no plans for MacOS support" (Nov 2025); "There are no plans to support macOS" (Nov 2023); Apple Silicon lacks SVE/SVE2 — [FEX issue #5046](https://github.com/FEX-Emu/FEX/issues/5046); [FEX discussion #3267](https://github.com/FEX-Emu/FEX/discussions/3267)
- CodeWeavers: CrossOver Preview with native ARM64 (31 Jul 2026); timeline "FEX was integrated in November 2025 ... in July 2026 a macOS-compatible FEX was finished" — [CodeWeavers on X](https://x.com/CodeWeavers/status/2083178481186185606); [CodeWeavers blog (JS-gated)](https://www.codeweavers.com/blog/mjohnson/2026/7/31/crossover-preview-the-right-to-bear-arm64-on-mac); Wine side LGPL, to be published with CrossOver 27 sources early 2027; preview requires macOS 26.5+ (third-party tracker) — [highball issue #6](https://github.com/gauthierpiarrette/highball/issues/6); confirmed by Brendan Shanks on wine-devel — [wine-devel thread](https://list.winehq.org/hyperkitty/list/wine-devel@list.winehq.org/thread/CKG5CEN2BE5VRXZ7O7NX4YUSBH3247WH/)
- dbc-hbin/FEX-darwin: builds `xtajit64.dll` (x64 via ARM64EC) and `xtajit.dll` (x86 WoW64) for ARM64-native Wine on macOS; "not a standalone loader"; Wine must supply hooks for shared-data reads, JIT write protection, native JIT allocation and the WoW64 guest window; patches: relocated `KUSER_SHARED_DATA` reads, nested JIT write scopes, executable-memory allocator with 16KB PE alignment, WoW64 guest address window adapted from willfaust/FEX PR #2 (MIT), pointer identity and whole-process code invalidation, 16KB guard pages, context/extended-state fixes; based on FEX-2609.1; needs llvm-mingw 22.1.8; disk caching opt-in; 10 commits, 3 stars, MIT — [FEX-darwin](https://github.com/dbc-hbin/FEX-darwin); [FEX-darwin v0.1.0](https://github.com/dbc-hbin/FEX-darwin/releases/tag/v0.1.0)
- Irz-Z/wine-macos-native v0.1.0 (published 17 October; year not shown but Wine 11.10 implies 2026): native ARM64 Wine 11.10 with in-process FEX, "no Rosetta 2 required"; TEB in pthread TSD slot 700 mapped to `TPIDRRO_EL0` to avoid macOS zeroing x18; `libarm64ecfex.dll` enabled with `WINEARM64ECEMU=1`; `libwow64fex.dll` provides an experimental ~4 GB 32-bit guest address window at `0x10000000000`, enabled with `WINEWOW64EMU=1`; prebuilt tarball with both DLLs — [wine-macos-native v0.1.0](https://github.com/Irz-Z/wine-macos-native/releases/tag/v0.1.0)
- MetalSharp-Wine: Wine 11.20 native arm64 macOS app with a non-upstreamed FEX fork; ARM64 Windows programs native, x86_64 via `libarm64ecfex.dll` with Wine DLLs as ARM64X hybrids, i386 via `libwow64fex.dll` in the signed app only; macOS 15+, i386 needs macOS 26.4+; graphics: Mullion (DXMT fork) default for D3D10/11/12, `GRAPHICS_BACKEND=dxvk` or `vkd3d`, WineMetalGL for OpenGL; Steam/Epic launcher fixes and a native Steam bridge; not a double-click app yet; references macOS 27 features; 223 commits, 16 stars — [MetalSharp-Wine](https://github.com/metalsharp/MetalSharp-Wine)
- Zagrios/FEX: Darwin port of FEXCore used by voile-lkd's Linux engine; host program `fexdarwin-run` embeds FEXCore and serves the guest's Linux syscalls; guest memory in a window at a host offset so a 47-bit guest space fits; `MAP_JIT` + `pthread_jit_write_protect_np`; async signals delivered only at guest-instruction boundaries; SMC tracked per host page; RDTSCP/RDPID on Apple silicon; only FEXCore ported (no tools/thunks/rootfs) — [Zagrios/FEX](https://github.com/Zagrios/FEX)
- A FEX "Windows on arm" discussion and the FEX wiki describe the generic mechanism (drop-in for xtajit64) that all these macOS ports reuse — [FEX discussion #5367](https://github.com/FEX-Emu/FEX/discussions/5367); [FEX wiki](https://wiki.fex-emu.com/index.php/Development:ARM64EC)
- SourceForge's unofficial mirror lists "macOS aarch64 M1 & Intel" among supported systems, contradicting upstream; the mirror is not affiliated with FEX — [SourceForge FEX mirror](https://sourceforge.net/projects/fex.mirror/)
- Box64: no macOS port, issue or PR found (GitHub search "macOS"/"Darwin" in ptitSeb/box64 yields only Asahi-on-Mac Linux issues) — [box64 issue #487](https://github.com/ptitSeb/box64/issues/487); the rukernel project lists FEX and Box64 in a plan for a Darwin userland, unrelated to a Box64 port — [rukernel issue #18](https://github.com/tamnd/rukernel/issues/18)
- FEX in a Linux VM on Mac hardware: Asahi muvm (Linux host, 4K-kernel microVM) — [Asahi blog](https://asahilinux.org/2024/10/aaa-gaming-on-asahi-linux/); podman-fex (macOS host): FEX inside a libkrun VM running Fedora CoreOS aarch64, kernel 6.19.10-200.fc43.aarch64, binfmt_misc + OCI precreate hook for amd64 containers, ~1.8 GB EROFS RootFS, QEMU-user fallback; M1 Max `podman run alpine echo` 2.1 s native / 2.8 s FEX cold / 2.4 s warm; Rosetta 2 + libkrun "is not viable"; Go 1.24+ crypto SIGSEGV, MSSQL crashes; "Preview Release" April 2026, tested macOS 26.4.1 / Podman 5.8 — [podman-fex](https://github.com/tnk4on/podman-fex); [podman discussion #28549](https://github.com/containers/podman/discussions/28549)

### Inferences
- Every working macOS FEX effort targets the Windows-DLL (ARM64EC/WoW64) form of FEX, not the Linux loader — consistent with the FEX wiki's point that those modules need only ntdll-level services. The hard parts each port lists are the same: 16K page alignment/guard pages, KUSER_SHARED_DATA placement below PAGEZERO, MAP_JIT/W^X write scopes, x18/TEB, and the 32-bit address window.
- The CodeWeavers port is the only one likely to ship to end users at scale, but its source will not be public until early 2027; FEX-darwin, MetalSharp and wine-macos-native are the open references in the meantime, all unmerged upstream.

### Gaps
- CodeWeavers has not (in any fetched source) said whether its macOS FEX changes will be upstreamed to FEX-Emu, only that the Wine side will ship with CrossOver 27 sources.
- No compatibility list or benchmark exists for any of the open macOS FEX forks; MetalSharp's numbers are self-reported.
- The willfaust/FEX PR #2 (32-bit guest window) referenced by FEX-darwin was not fetched.
- No evidence of UTM or Lima users combining FEX with Wine for games on macOS was found; podman-fex is container-focused, not gaming.
