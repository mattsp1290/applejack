# ADR-0003: Project-built, project-signed, notarized engine bundles

## Status

Accepted, 2026-10-28

## Context

The Gcenx cask is ad-hoc signed, is Wine 7.7, and contains D3DMetal. It can neither be republished nor serve as the long-term base. steamac proves that signing plus notarization works on a Wine tree.

## Decision

CI builds the x86-64 Wine payload from source in work package 3. It adds DXMT, vkd3d-proton, Vulkan ICDs, and GStreamer. It signs every Mach-O with the project's Developer ID, notarizes, and publishes one `.tar.zst` per engine version. `engines/manifest.toml` pins the published URL and SHA-256. The bundle build fails if any path matches a D3DMetal denylist.

For the native engine this decision is revised by the native ARM64 engine track (ADR-0008). That engine ships as signed app bundles with embedded provisioning profiles, because the entitlement cannot live in loose binaries.

## Consequences

The project owns a Wine source build, signing, and notarization in CI. Notarization of thousands of Wine files is slow and fragile, so it runs in CI only.

Rejected alternatives.

- Pointing users at Homebrew casks. They are unsigned, unpinned, and have D3DMetal inside.
- Bundling Wine inside the app. It makes a 1 GB app and blocks engine swaps.
